# 安装目录：上游 id 自动推导与包内名称唯一

「安装目录」页签的安装表单不再让用户填写上游 id。id 由目录项自动推导，用户只需确认安装名称。

## 为什么要自动推导

上游 id 是工具名前缀（`<upstream_id>__<tool>`），后端要求满足 `^[a-z][a-z0-9_-]{1,31}$` 且不含 `__`（`__` 是工具名分隔符）。让用户手填只会产生两类错误：正则不合法、与同包已装实例撞号。目录项自带 `default_upstream_id`，足以推出一个可用 id。

## 推导规则

`src/pages/upstreams/catalogNaming.ts` 的 `nextUpstreamId(entry)`：

1. 取 `entry.default_upstream_id`，去空白、转小写；
2. 非 `[a-z0-9_-]` 字符替换成 `-`，连续 `__` 压成 `_`，去掉开头的非小写字母；
3. 按包内已有 `installations[].upstream_id` 依次尝试：序号 1 用主名本身，之后 `-2`、`-3` …（`composeUpstreamId`）；
4. 主名过长时先截断到 `32 - 后缀长度`，再去掉截断点残留的 `-`/`_`，避免拼出 `foo--2` 或 `__`；主名被清空时回落 `pkg`；
5. 仍不满足正则（理论上不会）就继续递增，最多 1000 次，最后抛错而不是提交非法 id。

因为 id 是基于「当前已安装集合」算出来的，目录刷新后弹层里的只读提示会跟着变；提交时后端仍做最终判定，前端不做乐观假设。

## 包内名称唯一

名称默认 `entry.name`；已有同名安装时用 `entry.name (2)`、`(3)` …（`nextInstallationName`）。提交前 `installationNameError` 做两道校验：

- 去掉首尾空白后不能为空；
- 与同包其它安装的名称比较时忽略大小写（`trim().toLowerCase()`），冲突时返回「名称已被该包的其它安装使用，请换一个。」，不发请求。

唯一性只在包内成立：不同包允许同名实例，后端的上游名称本就允许重复，这里只是避免同包实例在列表/工具前缀上难以区分。

## 冲突与刷新

自动推导可能与并发安装撞号，后端返回 `MCP_UPSTREAM_CONFLICT`（409）时表单提示「上游 id 已被占用，目录已刷新，请确认新的 upstream_id 后重试。」并 invalidate `['mcp-catalog']`，让弹层拿到新的已装集合，用户再点安装即用新序号。不做自动重试循环。

## 目录展示

卡片只保留名称、id、版本、两行摘要、最多 3 个标签 + 余数、已安装数量；字段/工具/实例表全部进「详情」弹层，避免一屏堆满定义。详情与安装弹层都用目录刷新后的最新条目（按 id 从 query 结果里重新取），避免拿旧快照推导 id。
