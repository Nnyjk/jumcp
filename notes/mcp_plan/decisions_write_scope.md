# 业务数据写路径：整体否决

## 结论

- 本服务提供的全部 MCP tool 对**接入数据源只读**：只读账号 + 只读会话是唯一强保证，不存在写能力，也不预留写开关（主文档 §1.3、§4.3.1）。
- agent 可修改的只有**本项目自有数据**：能力定义（按版本追加）、生命周期与可见性、审计只能追加（§4.4.6）。组、角色、预算、数据源与凭证属部署配置，agent 不可改。
- 若未来确需"agent 改业务数据"，作为独立服务/独立项目重新立项，不并入本仓库的阶段规划。

## 否决理由

- **产品边界**：数据源权限由平台运维授权，本服务只消费；一旦承担写业务数据，就要承担业务一致性、误写与回滚责任，与"数据面工具提供方"的定位冲突。
- **安全面**：业务写需要独立写账号、审批、一次性令牌、幂等、影响行数控制与对账队列；这套机制与差异化功能（agent 自维护工具目录）无关，却显著扩大攻击面。
- **治理面**：真正需要被 agent 修改的是工具定义本身。把写能力放在业务库上，会让审计无法区分"改工具"与"改数据"。

## 仍然成立的外部约束（保留自被删方案）

- 只读必须落在账号与连接级（DSN 锁参数或 role GUC）；运行期 `SET default_transaction_read_only` 可被 `COMMIT; SET ...` 链式绕过，池化下还会污染共享连接。
- MCP `annotations` 是提示而非强制；安全边界在服务端策略与账号权限。
- 幂等键不能当凭据；客户端 elicitation 不能替代服务端审批。
- 客户端对 `notifications/tools/list_changed` 的支持度不一，发现面不能依赖热推送保证正确性。
