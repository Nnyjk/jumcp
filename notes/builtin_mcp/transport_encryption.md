# 传输加密：威胁模型与取舍

接口契约、错误码与线格式见 `docs/mcp-router.md` 的「3.5 传输密钥与密文提交」与
`docs/builtin-mcp.md` 的「3. 配置与密钥」。本文只记 docs 不适合承载的理由与限制。

## 1. 威胁模型：防什么、不防什么

**能防**

- 请求体被顺手记录：反向代理 access log（开了 body 记录）、APM/网关的请求采样、
  浏览器 DevTools 的「Copy as cURL」与表单回放、错误上报里夹带的 payload。密码在这些地方
  只是 `enc:v1:<hex>`，没有密钥就解不开。
- 抓包看到单次请求：明文密码不在报文里。短时间窗口内被重放到同一服务也只会得到同一份密文
  （nonce 每次随机，重放本身仍受管理鉴权与 TLS 约束）。
- 前端实现失误的低成本兜底：即便管理台把表单值写进日志，值也只是密文。

**不能防**

- 能读到管理页面的中间人：密钥就随页面下发，谁拿到页面谁就能加密，也能解自己抓到的密文。
- 已经拿到管理 token 的攻击者：他可以直接改配置，传输加密不增加任何授权强度。
- 拿到 `JUMCP_TRANSPORT_KEY` 的人解密历史报文；拿到 `JUMCP_SECRET_KEY` 的人解密库里密文。
- 磁盘或数据库泄漏：传输密钥不参与落库，库里的密文只能用 `JUMCP_SECRET_KEY` 解。

结论：它是「别让密码在请求日志/抓包里直接可读」的纵深防御，**不替代 TLS**。生产必须由网关
终止 TLS，管理面不能裸奔在明文 HTTP 上。

## 2. 为什么复用 `enc:v1` 线格式

- 两处是同一个密码学需求（AES-256-GCM + 随机 nonce + 可判别前缀），复用 `SecretKey` 的实现
  意味着只有一份 nonce 处理、一份 hex 编解码、一份 Debug 脱敏；第二套格式必然在半年后分叉。
- 前缀 `enc:v1:` 让「是不是密文」成为显式判断：服务端看到没有前缀的值直接拒绝，不会出现
  「猜一个格式失败就当明文用」的降级路径。
- 代价是两个用途共用实现、不共用密钥（见下），轮换语义因此不同：落库密钥换了旧密文不可解，
  传输密钥换了只影响还拿着旧密钥加密的请求，库里的密文不受影响。

## 3. 为什么用独立密钥

- 用途分离：传输密钥随页面下发（浏览器可见），落库密钥只在进程内。共用一把等于把落库密钥
  发给每个能打开管理台的人。
- 轮换粒度不同：怀疑抓包泄漏时只换传输密钥，重填一次密码即可；怀疑数据库泄漏时只换落库密钥，
  在管理台重填密码。共用密钥就只能两件事一起做。
- 审计口径：传输密钥从不参与落库，日志里也不需要为了「能不能解密」而多一条依赖。

## 4. 为什么鉴权端点下发，而不是编译进前端 bundle

- 编译进 `admin-web/dist` 的密钥等于公开常量：静态资源本来就是给所有访问者下载的，任何
  `grep` 构建产物的人都能拿到，这层加密立即归零。
- 走 `GET /admin/transport-key` 至少把「谁能拿到密钥」收窄到有管理鉴权的调用方，并且可以
  统一响应头 `Cache-Control: no-store` 防止中间缓存留下副本。
- 它仍然不是秘密分发机制（能读页面的人就能读这个响应），所以只在威胁模型第 1 节「能防」的
  范围内承诺；真正的边界是 TLS + 管理鉴权。

## 5. 轮换与故障

- 换 `JUMCP_TRANSPORT_KEY`：旧页面/旧脚本手里的密钥失效，再提交密码会 400
  `MCP_TRANSPORT_DECRYPT_FAILED`；刷新页面重填即可，库里的密文不需要重写。
- 换 `JUMCP_SECRET_KEY`：库里的密文全部不可解，必须在管理台重填每个已安装包的密码字段；
  轮换前备份 `registry.sqlite3`。
- 两把密钥都缺失或非法时 HTTP 模式启动即失败（fail-closed）；不会带病启动后把明文当密文用。
