# 旧审计行与 v2 边界：被否决的决定

记录审计载荷从「字段随意拼装」收敛为 14 键骨架时，**明确不考虑**的几种做法与理由。只记约束与取舍，不记改动过程。

当前契约见 `docs/audit-openness.md`。

## 1. 不回填旧审计

**否决做法**：给改造前的 `admin_change` / `tool_call` 行补写 `object_type` / `object_id` / `action`，让全表统一。

**理由**：

- 审计表是 append-only：`BEFORE UPDATE` trigger 直接 `RAISE(ABORT, ...)`。回填必须临时 `DROP TRIGGER`，等于给「改写历史审计」开一条通用通道；通道一旦存在，就再也无法用 trigger 证明历史未被改过。
- 每行的 `hash = sha256(canonical(envelope 去 hash) + prev_hash)`。任何字段回填都会改 payload，进而改本行 `hash`，其**后继所有行**的 `prev_hash` 全部失效——哈希链从回填点开始断裂，`/health` 的 `audit_chain` 会永久变成 `tampered`。
- 回填是**推测**而非事实：旧行的 `diff` 同时承载动词（`create`）、状态迁移串（`draft->review`）和变更后取值 JSON（`{"callable":true}`），旧 `approval_id` 同时承载自动溯源串（`submit:alice`）与人工票号（`ap-e2e-1`）。要从这些值反推 `object_type` / `action` / `approval`，得到的是推断结果，不是当时发生的事实。审计要的是可证据化的记录，不是补齐后的漂亮表格。
- 旧行数量有限且已归档，保留原样即可回答「当时记录了什么」；新契约只需要对**新发生的事件**成立。

## 2. 不做旧字段回退

**否决做法**：读取端在缺少 `object_type` 时回退读 `capability_id`，缺少 `action` 时回退解析 `diff` 字符串，缺少 `approval` 时回退读 `approval_id`。

**理由**：

- 回退会把被废弃的**歧义**重新引入当前接口：`diff` 的三形态、`approval_id` 的双语义会以「兼容」名义继续进入统计、界面和下游报表，v2 的收敛就白做了。
- 回退无法判定边界：`diff="create"` 是动词，`diff="draft->review"` 是迁移，`diff="{...}"` 是变更后取值——一个字段三种解析分支，任何一处写错都会静默给出错误语义，而审计场景的错误不做静默降级。
- 显式的「旧格式」比「看起来统一、实则两种来源」更诚实：管理台对缺结构化键的事件统一标注「旧格式事件，仅原始载荷」，并提供原始 payload 全文；使用者知道自己在看什么。
- 判定条件是结构性的——`object_type` / `object_id` / `action` 三者任一缺失即为旧格式——不需要版本号或时间戳阈值，也不会因为某条旧行恰好有 `object_id` 而误判。

## 3. stats / calls 只认 v2 `object_id`

**否决做法**：工具统计与调用明细改用「`payload.tool` / `payload.template_id`（旧）或 `object_id`（新）」的双路读取，尽量把旧调用也纳入聚合。

**理由**：

- 双路读取会让**同一个指标有两种口径**：旧行的 `tool` 是工具名（`db_query_readonly`）、新行的 `object_id` 是对象标识（也可为模板 id）；旧行缺 `error_code` / `bound_params` / `data` 结构，成功/失败、重试、缓存、token 的可得性都不同。混在一起算出的成功率没有明确分母。
- 旧行没有 `object_id`，就无法回答「这条事件作用于哪个对象」；`calls` 是按 id 聚合的视图，硬塞进去只能靠字符串猜测归属。
- 统计缺口的代价是**可见且可解释**的（旧调用计数为 0），口径混淆的代价是**不可见**的（数字看着连续，其实两套语义拼接）。前者可以在界面上用一句「仅统计审计 v2 事件」说明，后者无法向审计解释。
- 因此边界写死：只有带 `object_id` 的事件进入台账与明细；`object_id` / `object_type` 过滤同样只匹配新格式。旧事件仍可在「审计查询」按 `event_type` / 时间窗检索，并查看原始载荷——查得到，但不进聚合。

## 4. 旧行保留原始载荷

**否决做法**：旧行只保留 `event_id` / `ts` / `actor` / `event_type`，其余 payload 折叠丢弃，或统一渲染成「历史数据不可用」。

**理由**：

- 旧载荷里的事实（当时的 SQL、入参、错误码、`before_hash`/`after_hash`、`approval_id` 原文）是唯一的历史证据；丢掉它换来的只是界面整齐。
- 旧行的歧义是**已知的、可以在视图层说明的**：把 `capability_id`、`diff`、`approval_id` 的原文照实展示，读者自己判断即可；这比替换成推断值更可靠。
- 新版渲染只依赖结构化字段，遇到旧行不报错、不猜测、不隐藏：标注「旧格式事件，仅原始载荷」并展示 `payload` 原文，是唯一不制造新语义的呈现方式。
- 保留原始载荷也让 v2 的字段演进可追溯：能对比「同一动作当年记了什么、现在记了什么」，这本身是改造是否收敛的证据。

## 5. 坑：payload 顶层用 `schema_version`，不用 `version`

**现象**：v2 骨架最初把载荷结构版本放在顶层 `version`，与 `data.version`（能力/模板业务版本）同名。结果是同一份 payload 里出现两个 `version`，含义完全不同：一个是「这份 JSON 的骨架版本」，一个是「这个能力是第几版」。

**后果**：

- 消费方按 `payload.version` 取业务版本时，实际拿到的是结构版本（恒为 `1`），并且在能力升到 v2 后依然显示 `1`——错误不报错、只是静默错值。
- 反序列化侧如果按 `version` 建模型，两个来源会互相覆盖；「没有版本」与「结构版本」也无法区分。
- 顶层键名被业务字段占用后，未来结构升级没有干净位置可用。

**结论**：载荷结构版本固定命名为 `schema_version`（当前恒 `1`），并从顶层移除 `version`；业务版本只出现在 `data.version`。两者**任何时候都不共用键名**，也不在顶层为业务字段留同义别名——历史数据中若已经存在旧键名，按旧格式处理，不做别名回退。
